# Repo Analysis: learning-to-self-evolve

**Path:** `refs/related-work/Learning-to-Self-Evolve/repo/` · **Source:** https://github.com/chenyn66/learning-to-self-evolve · **Analyzed:** 2026-09-14 (commit `9eb5eac`, "Add LSE code", 2026-06-18 — the only commit)

## Overview

- **Paper:** Learning to Self-Evolve (see `paper_analysis.md`)
- **Framework:** two halves — a self-contained `lse/` package for the test-time evolution loop (vLLM or any OpenAI-compatible endpoint, Hydra configs, no trainer), plus a vendored veRL fork under `verl/` carrying four LSE-specific files for the training half
- **RL Algorithm:** clipped policy gradient with the pre-edit score as the baseline, registered in veRL as advantage estimator `delta`; no critic, no KL penalty, no group normalization
- **Base Model:** Qwen3-4B-Instruct-2507 for both the action policy and the self-evolving policy (the shipped default config still names Qwen2.5-1.5B-Instruct); Arctic-Text2SQL-R1-7B for the transfer experiment
- **Key Innovation:** the reward is `post_edit_holdout_accuracy - pre_edit_holdout_accuracy`, computed by actually re-running the task under the candidate prompt, and that scalar is used directly as the advantage

There is no top-level README. The release is complete enough to run — code, configs, launch scripts, and the small data assets — but ships no trained checkpoint and none of the roughly 4,000 evolution-tree nodes the paper trains on; those must be regenerated by running the evolution loop 200 times.

## Component Inventory

### 1. Entry points

| Script | What it does |
|---|---|
| `main.py:12` | Hydra `@main`; picks `BirdSimulator` / `MMLUSimulator` (`run_self_evolve()`) or the GEPA baseline simulators. Everything is config-driven; the only positional concept is the task. |
| `scripts/run_bird.sh:10` | `python main.py task=bird "$@"` after sourcing `.env.local`. |
| `scripts/rl/train_bird_ppo.sh:65` | `python -m verl.trainer.main_lse_ppo` with ~45 overrides. This file is the real hyperparameter record. |
| `verl/verl/trainer/main_lse_ppo.py:33` | Subclasses veRL's `TaskRunner` so the reward pool is allocated without spawning a `RewardModelWorker` — the reward is a function, not a model. |

### 2. Special token / action handling

Two tags, both parsed by `lse/helpers.py:197 extract_from_tag`, which matches the opening tag corresponding to the **last** closing tag so nested tags survive. The action model returns its answer in `<answer>...</answer>`; the self-evolving policy returns the new instruction block in `<prompt>...</prompt>` (`lse/agents/bird_agent.py:401,407`). Generation is retried up to `max_tries` (default 3) with a checker that simply asks whether the tag was found. One wart: `lse/helpers.py:204` branches on an environment variable `USE_ARCTIC` to fall back to SQL-fence extraction for the Arctic model.

### 3. Environment / tool interaction

The action model is reached over HTTP through an OpenAI-compatible endpoint (`lse/agents/base.py:77` client construction; `:262` the chat call with retry and timeout logging; `:353` thread-pool parallel chat; `:377` in-process vLLM bring-up as the alternative). During RL, `lse_reward_fn.py:47 _build_model_url` points the scoring environment at the vLLM router address that veRL passes in, so reward computation and rollout generation run on separate GPU pools. Task scoring for BIRD is real SQL execution against the SQLite database (`lse/bird/eval.py`), with a process-wide result cache and a 30-second timeout; `NUM_SQL_WORKERS` bounds the executor.

### 4. Token masking

Nothing LSE-specific — the proposer emits one response per prompt and the whole response is trained on. Standard veRL masking applies.

### 5. Reward function — the piece that matters most here

`verl/verl/utils/lse_reward_fn.py:183 compute_score` is the entire reward:

```python
new_prompt = extract_from_tag(solution_str, "prompt")
new_prompt = new_prompt.strip() if new_prompt is not None else ""

if new_prompt is None or len(new_prompt) < 10:
    return {"score": INVALID_REWARD, "reward": INVALID_REWARD, "performance": float(extra_info["performance"])}
...
reward = float(score - extra_info["performance"])
```

with `INVALID_REWARD = -1.0` (`:22`). `score` comes from `_compute_bird_score` / `_compute_mmlu_score`, which rebuild the *same* holdout environment the node was scored on — `BatchBird.create_test_envs(config, extra_info["test_env"])`, where `test_env` is the `env/info.json` written by the evolution run and contains the database id plus the fixed `holdout_qids` (`lse/envs/bird_env.py:207`) — install the candidate instructions, generate `test_n_eval` samples per problem, and average execution accuracy. `extra_info["performance"]` is the stored pre-edit holdout score of the node being edited (`lse_dataset.py:84`). There is no term for anything other than post-edit accuracy on that one fixed set: no cost term, no length term, no check against problems the old prompt already solved, no evaluation on any other domain.

Three properties worth naming: the invalid-format floor at $-1.0$ is subtracted from the pre-edit score too, so a malformed proposal is punished far harder than a merely harmful one; the reward is asynchronous and slow because it runs the full task pipeline per candidate (the file is built around two semaphores and a 200-thread pool for exactly this reason); and the same 50 problems are re-scored for every candidate of every node, which is what makes the pre-edit score a valid baseline and also what makes the holdout heavily reused.

### 6. RL training loop

`verl/verl/trainer/ppo/core_algos.py:333 compute_delta_outcome_advantage` — the advantage is the scalar reward broadcast over response tokens, with optional standard-deviation scaling or whitening across the batch, and **no group mean subtracted**:

```python
@register_adv_est("delta")
def compute_delta_outcome_advantage(token_level_rewards, response_mask, config=None, **kwargs):
    scores = token_level_rewards.sum(dim=-1)
    ... # optional std_norm / whitening over the batch
    advantages = scores.unsqueeze(-1) * response_mask
    return advantages, advantages
```

This is eq. 9 of the paper made literal: the pre-edit score already played the role of the baseline inside the reward, so no further baseline is estimated. Launch-script settings that define the algorithm (`scripts/rl/train_bird_ppo.sh:73–101`): `algorithm.adv_estimator=delta`, `algorithm.use_kl_in_reward=false`, `actor.use_kl_loss=false`, `critic.enable=false`, `rollout.n=8` (the paper's Appendix A says 4), `data.train_batch_size=16` (Appendix A says 32 nodes), `max_prompt_length=65536` (the proposer's prompt carries the action model's full reasoning for every problem in the batch), `max_response_length=16384`. A sibling estimator `logit_delta` (`:368`) exists but is not used by either launch script.

### 7. SFT / cold-start pipeline

Absent. Training is on-policy from the released base model; the only "cold start" is the offline generation of evolution trees with an untrained proposer.

### 8. Data pipeline

`verl/verl/utils/dataset/lse_dataset.py` turns finished evolution runs into RL training data. Each run directory contributes `tree/tree.json` (every node's instructions, summary, conversation, holdout performance, parent link), `env/info.json` (database id and holdout question ids) and `env/config.yaml`. Every node with a non-NaN performance and a stored `self_evolve_prompt` becomes one training example whose prompt is the exact proposer prompt that node saw at evolution time (`:68`), and whose `extra_info` carries the pre-edit `performance`, the holdout descriptor, and the full run config so the reward function can rebuild the environment. Duplicate prompts are dropped. Curriculum (`:53`, `:111`): `tree.calculate_improve_potential()` sets each node's `improve_potential = max_performance_in_its_tree - node_performance`, examples below `min_improve_potential` are filtered out, and `ordered_by: improve_potential` sorts the dataset so the nodes with the most headroom come first. This is the code behind the paper's "simple curriculum by preferentially sampling nodes with the highest improvement potential."

The tree itself (`lse/core/tree.py:183 save_tree`, `:215 load_tree`) is a plain JSON round-trip — a node is `(id, parent_id, depth, visits, performance, round_idx, instructions, conversation, summary, history, self_evolve_prompt)`.

### 9. Multi-GPU / infrastructure

veRL defaults: FSDP actor, vLLM rollout, Ray. The launch script splits GPUs between a training/rollout pool and a reward pool (`TRAIN_N_GPU`, `REWARD_N_GPU`, `ROLLOUT_TP/DP`, `REWARD_TP/DP`), because reward computation is itself a generation-heavy workload — the action model must answer 50 holdout problems, `test_n_eval` times, per candidate edit. `reward_model.enable_resource_pool` toggles whether the reward gets its own pool or shares the global one.

### 10. Evaluation

Execution accuracy for BIRD (`lse/bird/eval.py`, comparing result sets of the predicted and gold SQL, with caching and timeout) and exact letter match for MMLU-Redux. Round-level metrics are logged to Weights and Biases (`average_accuracy`, `best_acc`, `dev/avg_acc`, `dev/best_acc`, `test/selected`). `base_simulator.py:80 _maybe_log_kfold_cv` implements a k-fold cross-validated round-selection metric — for each fold, pick the round that was best on the other folds and report that round's accuracy on the held-out fold — which is a more honest version of the paper's best-over-rounds number, but the reported protocol uses `k_fold: 1`, i.e. off.

## Relevance to this project

### Components we can directly reuse

- `verl/verl/trainer/ppo/core_algos.py:333` — the `delta` advantage estimator is a 20-line drop-in for any reward whose baseline is known before the action. Our per-edit objective has exactly that shape: current-batch task performance is measured under the harness as it stood before the edit, so the pre-edit score is available as a free baseline.
- `verl/verl/utils/lse_reward_fn.py` as a structural template for an edit-scoring reward: a candidate edit is extracted from tagged output, applied to a rebuilt environment, scored by actually running the task, and reduced to a scalar — with the invalid-proposal floor and the two-semaphore concurrency pattern that keeps a slow reward usable inside an RL loop.
- `lse/core/tree.py` plus `verl/verl/utils/dataset/lse_dataset.py` as the pattern for turning finished evolution runs into a training set of harness states with recorded values, including the starting-state fix: train from nodes the system itself produced, not only from the seed. Any trained proposer of ours needs this or it will be trained on a state distribution it never sees at deployment.

### Components we need to modify

- **The reward's horizon.** `reward = score - extra_info["performance"]` scores the edit on one evaluation immediately after it, on a set drawn from the same domain, and never looks further. Adding our plasticity term means the reward needs a second, state-level component evaluated on the harness *after* the edit, and the tree's stored node value needs to become a discounted sum over later rounds rather than a one-round score. Note the paper's own eq. 8 argument cuts in our favour: an action-independent offset is absorbed by any baseline, but an estimate of future stream performance depends on the edit, so it survives group normalization and is not absorbed.
- **The scored set.** `create_test_envs` rebuilds one fixed holdout inside one database. A retention check needs a second set — previously passed problems accumulated from the stream, from domains other than the current one — re-scored at commit time. Nothing in the reward path forbids this; it is one more environment built from a different id list.
- **The edit surface.** `build_evolve_prompt` / `_self_evolve_impl` rewrite exactly one string, the instruction field. Supporting more than one layer means the proposer's output must name what it edits and the applier must route it, which the current single-`<prompt>`-tag contract cannot express.
- **The reported metric.** `run_self_evolve` returns the accuracy history and the harness reports the max; a stream-performance integral needs the per-round series and the k-fold path (`base_simulator.py:80`) turned on.

### Components that don't apply

The GEPA and TextGrad baseline wrappers (`lse/gepa/`, `lse/textgrad_baseline.py`) are prompt-optimizer comparisons in a single domain; the BIRD SQL execution scorer and MMLU letter matcher are task-specific. The whole `verl/` fork is a heavy dependency that is only worth adopting if we train a proposer with veRL.
