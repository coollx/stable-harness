## 1. Method Motivation

### a) Why was this method proposed?

The paper's premise is ours: "The capacity of modern agents depends not only on the underlying model, but on the mediation imposed by the surrounding harness" (Sec. 1). Its driving complaint is that harness development is not yet an engineering discipline. Three gaps are named in the introduction. First, harnesses are hand-engineered and static: "any change in model version, tooling, or problem domain requires bespoke modification, with no mechanism for experience-driven improvement." Second, they are architecturally entangled: prompt templates, tool wrappers, retry policies, and memory live in the same code paths, "so changes to one component silently break others, and reuse across domains reduces to copying rather than composition." Third, harness engineering and model training run independently: "trajectory data collected while improving the harness is discarded rather than incorporated into model training."

### b) Pain points of existing methods

Related work is faulted along a ladder of increasing scope (Sec. 2.1-2.2). Primitive libraries (LangChain, LlamaIndex, Smolagents) "do not support harness-level composition: two harnesses built from identical primitives may still differ in structure." Orchestrators (LangGraph, AutoGen, CrewAI, Letta) "impose a particular control loop, so combining patterns, replacing components, and porting enhancements across tasks mostly remain manual." Productized harnesses (Claude Code, Cursor, Manus, DeerFlow) "remain architecturally static, evolving only through manual iteration." Prompt optimizers (APE, OPRO, EvoPrompt, Promptbreeder, ProTeGi, TextGrad, DSPy, MIPRO) establish instructions as learnable "but harness-level features (tools, memory, control flow) remain outside the optimization scope." Workflow optimizers (GPTSwarm, ADAS, AFlow, AgentSwift, ResMAS, EvoAgentX) cover "inter-component relations but not the full harness" because tool implementations, memory policies, and node-internal prompts stay static. Explicit harness-evolution work (SICA, Darwin Godel Machine, HyperAgents, Meta-Harness, Agentic Harness Engineering, Life-Harness) is credited with establishing observability as necessary, but faulted because "their designs lack a unifying theoretical framework that connects observed failure modes to principled defenses."

### c) Core hypothesis / intuition

If the harness is reified as a typed, substitutable object, then harness evolution can be cast as a Markov decision process over symbolic artifacts, and the known pathologies of reinforcement learning (reward hacking, catastrophic forgetting, under-exploration) become predictable design risks each of which can be met by a dedicated architectural defense; the same execution traces that drive harness edits can additionally train the model.

## 2. Method Design (PRIMARY FOCUS)

### a) Pipeline overview: Input to Processing to Output

HarnessX is three layers stacked: a composition substrate (Sec. 3), an evolution engine over it (Sec. 4), and a model-training loop sharing its traces (Sec. 5).

**Composition layer.** An agent is the pair $\mathcal{H} = (\mathcal{M}, \mathcal{C})$, where $\mathcal{M}$ is a model configuration ("which model serves which role — `main`, `judge`, `evaluator` — and the fallback policy") and $\mathcal{C}$ is a harness configuration ("how the agent behaves independently of model identity"). They combine as `agent = model_config.agentic(harness_config)`. The harness configuration decomposes as $\mathcal{C} = (\mathbf{P}, \mathbf{S})$, where $\mathbf{P}: \mathcal{H}ook \to \mathrm{List}[Processor]$ is a hook-indexed processor list and $\mathbf{S}$ is a fixed set of shared slot resources (tool registry, tracer, workspace, sandbox provider, plugin list). Table 1 fixes eight lifecycle hooks and what each may modify: `task_start` (system prompt), `step_start` (structural history edits), `before_model` (last user content; one user-message append), `after_model` (response content, tool calls), `before_tool` (tool input, approval flag), `after_tool` (tool result), `step_end` and `task_end` (read-only).

**Evolution loop (Algorithm 1).** Starting from an initial harness $\mathcal{H}_0$, each round $t$ runs: sample an adaptation batch $B_t$; run $\mathcal{H}_t$ on it, collecting traces $\Delta\mathcal{T}_t$ and per-task verifier scores; then four stages, each driven by the same meta-agent language model, which decides at each stage whether to continue:

1. **Digester** (selective) — compresses the round's raw traces into a per-task structured summary: "binary outcome, failure category (if any), implicated component identifiers, and supporting evidence excerpts", plus cross-iteration continuity linking each task to its history of prior outcomes and shipped edits. On GAIA this reduces roughly 10M raw trace tokens to roughly 10K structured summary tokens. Exits the round if actionability falls below a threshold.
2. **Planner** (selective) — builds an "adaptation landscape": which tasks are failing, what edits have been attempted, which components are implicated, and which edit types remain untried. This is the paper's dedicated defense against under-exploration: by constructing the landscape before edits are generated, "it prevents the pipeline from converging on trace-conditional local repair."
3. **Evolver** (selective) — produces $K_t$ candidate harnesses, each a typed builder operation on $\mathcal{H}_t$ carrying a *change manifest*: edited components, intended behavioral effect, and the tasks expected to improve or regress. New executable code must come with a smoke test showing the processor instantiates and runs.
4. **Critic and deterministic gate** (mandatory) — the Critic compares each manifest against trace evidence and returns `no_op` or an ordered `ship_ranking`; the deterministic gate then applies acceptance checks in sequence: manifest completeness, configuration normalization, build or smoke tests, and the **seesaw constraint** (a regression check on previously passing tasks). The first failing check halts the sequence. "This decouples language-model judgment from acceptance: regardless of the Critic's recommendation, only deterministic checks govern shipping."

A round commits a new harness only when a candidate clears every acceptance check; otherwise $\mathcal{H}_{t+1} = \mathcal{H}_t$ and an idle counter increments, with early stopping after patience $P$ consecutive idle rounds.

**Variant isolation via ensemble routing (Sec. 4.5).** With one harness, an edit that helps one subset may regress another and be rejected outright. Instead the system may keep up to $K$ harness variants and route each task to the variant with the highest estimated success rate on that task's cluster over prior rounds. When a candidate improves a subset while regressing others, the system forks a new variant rather than discarding the edit; the seesaw constraint is then scoped per variant.

**Co-evolution (Sec. 5.1).** Seven steps per iteration: rollout $(\mathcal{M}_t, \mathcal{H}_t)$ on $B_t$ with full tracing; a fixed verifier scores each trace; scored traces enter a fixed-capacity first-in-first-out replay buffer tagged with the harness version that produced them; AEGIS reads the buffer and may commit one harness edit; a forward pass caches token-level behavior log-probabilities for the new traces; a Group Relative Policy Optimization (GRPO) step updates the model; repeat with $(\mathcal{M}_{t+1}, \mathcal{H}_{t+1})$. "Every trace serves as both AEGIS diagnostic evidence and GRPO training signal", and harness update and model update "read the same buffer but neither conditions on the other's output within the same iteration."

### b) Architecture components

**Processor.** Every per-step behavior satisfies `async def process(self, event: Event) -> AsyncIterator[Event]`, consuming one event and yielding one of five outcomes: pass-through, transform, split, intercept (yield nothing, blocking propagation), or interrupt (raise, halting the loop). Because input event type equals output event type per hook, processors compose by sequential application and can be inserted or removed without breaking type correctness. Three class-level metadata fields govern composition: `_singleton_group` (mutual exclusion, at most one processor per group), `_order` (`PRE` / `NORMAL` / `POST` within a hook), and `_after` (soft dependencies on other singleton groups).

**The nine behavioral dimensions (Sec. 3.3)** — this is the paper's layer decomposition: model selection, context assembly, memory management, tool ecosystem, execution environment, evaluation and reward, control and safety, observability, training bridge. "AEGIS edits span all nine dimensions during evolution: context assembly and tool ecosystem are the most frequent edit targets, while observability provides the trace substrate on which AEGIS itself reasons, and the training bridge supplies trajectory records for co-evolution."

**The logged edit buckets.** Nine dimensions is the nominal space; the change-manifest schema (Table 9, Appendix B.3) records `bucket` as exactly one of four values — `prompt`, `tools`, `config`, `processor` — optionally a list. Every analysis figure in Appendix D reports shipped edits under exactly these four buckets. So the realized action space is: rewrite system-prompt templates, author a new tool implementation, retune an existing component's keyword arguments, or author a new middleware processor. The manifest's other fields are `candidate_id`, `capability_evidence` (verified claims that the edit mechanism actually works), `file_changes` (path / create-modify-delete / one-line summary), `predicted_impact` (`tasks_will_unlock`, `tasks_will_stabilize`, `tasks_at_risk`), and `attribution_signature` (a trace feature that must appear if the edit fired, e.g. a named tool call with a minimum call count).

### c) Formulas and algorithms

**Definition 1 (harness configuration)**: $\mathcal{H} = (c_1, \dots, c_9)$, each $c_i \in \mathcal{C}_i$ instantiating one of the nine dimensions, with $\mathcal{C}_i$ constrained by hook-type contracts and singleton-group exclusion.

**Definition 2 (harness edit)**: a function $e: \mathcal{H} \to \mathcal{H}$ modifying one or more dimensions while preserving type contracts. "The action space $\mathcal{E}$ is *discrete but open-ended*: each edit is a code-level artifact (new processor source, modified prompt template, reconfigured tool registry, or control-flow rewrite) generated by the meta-agent, not selected from a pre-enumerated set. Combinatorial explosion is managed not by exhaustive search but by the language model's generative capacity ... and by type constraints that prune invalid compositions at generation time."

**Definition 3 (operational mirror)**: the tuple $(\mathcal{H}, \mathcal{E}, \mathcal{R}, \mathcal{T})$, where $\mathcal{R}: \mathcal{H} \times \mathcal{E} \to \mathbb{R}$ "maps a configuration-edit pair to a scalar reward (verifier scores aggregated over an adaptation batch)" and $\mathcal{T}$ is the trace store. Table 2 states the correspondence: policy = harness-update procedure $\pi_{\mathrm{evo}}$; state $s_t = (\mathcal{H}_t, \mathcal{T}_t)$; action $a_t$ = typed harness edit; feedback = trace plus verifier score; update $\mathcal{H}_{t+1} \leftarrow U(\widetilde{\mathcal{H}}_t, \mathcal{T}_t, r_t)$ via a deterministic acceptance gate.

**The MDP instantiation, stated plainly and in full** (Sec. 4.1): apply $a_t \sim \pi_{\mathrm{evo}}(\cdot \mid s_t)$ to get $\widetilde{\mathcal{H}}_t = a_t(\mathcal{H}_t)$; run the candidate "on an adaptation batch (with the fixed model $\mathcal{M}$)" producing new traces and per-task verifier scores $r_t$; the acceptance operator "either commits the candidate ... or rejects it ..., enforcing the seesaw constraint: the candidate must not regress any previously solved task recorded in $\mathcal{T}_t$."

Three properties of this objective matter and are worth stating plainly, because they are consequences of the definition rather than of any one design choice. First, **there is no discount factor and no future term anywhere in the paper** — the reward is defined as the verifier score on the adaptation batch the edit was made for, so the edit's value to later batches never enters the acceptance decision. Second, **the "previously solved" set is the same fixed evaluation set re-scored every round** (Appendix A.2: "The same evaluation set for each benchmark is re-scored at every round"), so the retention check is a no-worse-than check against a fixed task list, not against a set accumulated from an arriving stream. Third, **the constraint is per-edit and per-task-binary**: a candidate must not flip any currently-passing task to failing under pass@2; the paper's own failure analysis (below) shows what this misses.

**Cross-harness grouping (eq. 2)**: $\mathcal{G}_x = \{\tau_i \in \mathcal{B} \mid \mathrm{task}(\tau_i) = x\} = \bigcup_k \{\tau \sim \mathrm{Agent}(\mathcal{M}_k, \mathcal{H}_k, x)\}$ — all trajectories for a task form one GRPO group regardless of which model checkpoint or harness version produced them, "so that within-group variation reflects strategy differences rather than sampling noise alone." **Advantage (eq. 3)**: $\hat{A}(\tau_i) = (r_i - \mu(\mathcal{G}_x)) / (\sigma(\mathcal{G}_x) + \epsilon)$. **Objective (eq. 4)**: a clipped policy-gradient objective with a Kullback-Leibler penalty against a fixed reference $\pi_{\mathrm{ref}} = \mathcal{M}_0$; **(eq. 5)** the importance ratio $\rho_i(\theta) = \pi_\theta(\tau_i \mid x) / \pi_{\theta_{\mathrm{old}}}(\tau_i \mid x)$, where $\pi_{\theta_{\mathrm{old}}}$ is the checkpoint that generated $\tau_i$ and cannot be recovered from any single live model — so token-level log-probabilities are cached to disk at buffer insertion and reused at every gradient step. The buffer is capped at $C$ trajectories with $s$ samples per round, bounding the maximum model-version lag at $\lfloor C/s \rfloor$ rounds. Alignment is at task level, not action level: "trajectories from different harness versions are grouped by task identity and compared by verifier reward alone", so harness versions with incompatible action spaces coexist in one group, and each trajectory is replayed under the harness that produced it.

**Pass@k (eq. 6)**: the standard unbiased estimator; all evolution curves use pass@2 (two independent rollouts per task per round, solved if either succeeds).

## 3. Comparison with Existing Methods

### a) Fundamental differences

Against prompt and workflow optimizers, the difference is scope: HarnessX's edit space includes tool implementation source and middleware code, not only instructions and inter-component wiring. Against productized harnesses, the difference is that the configuration is a serializable, comparable, substitutable value rather than code paths. Against prior harness-evolution systems (SICA, Darwin Godel Machine, HyperAgents, Meta-Harness), the difference the paper claims is the operational mirror: casting evolution as a Markov decision process over symbolic artifacts so that named reinforcement-learning failure modes become a design checklist with one architectural defense each. Against every one of them, including Harness Continual Learning (HCL), the co-evolution loop is genuinely new: the same traces that drive harness edits also train the task model, at no additional rollout cost.

Against HCL specifically, the two systems converge on the same shape from different directions and differ in three concrete ways. HCL's commit gate is a conjunction of current-batch improvement, bounded anchor loss, and validity; HarnessX's gate is manifest completeness, configuration normalization, a smoke test, and no regression on previously passing tasks — HarnessX does **not** require the candidate to improve the current batch (the Critic only ranks candidates by expected improvement), while HCL makes current improvement a necessary condition. HCL's mutable state excludes outer tools by construction (only inner skills distilled from memory are editable); HarnessX writes new tool source and new middleware. HCL grows an anchor set from the stream and sweeps a tolerance over it; HarnessX re-scores one fixed evaluation set every round, so its retention check is over a constant task list.

### b) Key innovations and their significance

1. **The typed composition substrate with per-hook type contracts and singleton groups — significant.** It is the precondition for scoping an edit's blast radius, and it is what makes variant isolation implementable rather than ad hoc. Section 7.1 argues the analogy honestly: "types do not generate correct programs, but they make incorrect programs *detectable*."
2. **Cross-harness GRPO with task-level (not action-level) grouping — significant.** Grouping trajectories by task identity across harness versions lets the model be trained on trajectories whose tool schemas and prompt structures differ, which is exactly what a system that rewrites its own action space needs. The cached-behavior-log-probability trick that makes this off-policy training cheap is a real engineering contribution.
3. **Variant isolation via ensemble routing — notable.** It converts "reject the edit" into "fork a variant", which is the paper's only working answer to accumulated regression, and it is validated (Sec. 6.3).
4. **The operational mirror as a taxonomy — incremental, and the paper says so.** Section 7.3: "The RL-symbolic-space mirror is a design heuristic, not a formal framework ... We therefore treat the mirror as a design checklist rather than a predictive theory: it identifies failure modes to defend against but does not predict their ordering, timing, or relative severity."
5. **The four-stage evolver pipeline — incremental by the paper's own ablation.** Section 6.4 finds a single-agent evolver reaches comparable accuracy (86.4% vs 87.4% on GAIA, within sampling noise at $n=103$), with the four stages buying roughly 12% fewer tokens and auditability, not accuracy.

### c) Applicability

HarnessX excels where a fixed evaluation set has a concentrated, mechanically-addressable failure cluster and the task agent is weak relative to the harness's reach: gains are inversely scaled with baseline performance (Sec. 6.2, 7.4). It struggles exactly where our project lives. Its scope statement is explicit (Sec. 6.1): "All reported gains are measured on the same task set used for evolution; held-out generalization to unseen tasks is not evaluated in this work." There is no arriving stream, no score-before-update protocol (the same tasks are re-scored under old and new harness alike), no late labels, and no notion of the harness's remaining capacity to be edited later. Read against our claim, HarnessX is a second, better-instrumented instance of the horizon $\gamma = 0$ case: the reward is the verifier score on the current adaptation batch and nothing after it, and the only forward-looking machinery is prose in the meta-agent's prompt ("Do not chase single-task wins that weaken the overall benchmark") plus a per-edit no-regression check. Its own failure analyses are the best external evidence we have that this is insufficient.

### d) Comparison table

| Method | Advantages | Disadvantages | Potential improvements |
|---|---|---|---|
| HarnessX / AEGIS | Edit space reaches tool and middleware source; typed substrate makes edit scope explicit; full trace observability with falsifiable per-edit predictions; variant isolation keeps the aggregate trajectory non-degrading; co-evolution trains the model on the same traces for free | Reward is the current adaptation batch only; no held-out evaluation at all; retention is a per-edit binary check that provably misses sub-threshold accumulation; requires a frontier closed-weight meta-agent (100M-175M tokens per benchmark) | Score an edit against later batches rather than its own; measure the harness's remaining editability directly rather than inferring it from a decaying prediction hit rate; keep a growing anchor set drawn from the stream instead of one fixed evaluation set |
| HCL | Explicit retention criterion over an anchor set with a sweepable tolerance; a stream of heterogeneous tasks; joint versioning of the whole harness state | Current-batch improvement is a necessary commit condition; outer tools and weights never change; plasticity named but never measured | Estimate plasticity rather than fixing a tolerance |
| Prompt and workflow optimizers (DSPy, AFlow, ADAS, GPTSwarm) | Mature, cheap, well-studied search over instructions and inter-component structure | Component-level artifacts (tool implementations, memory policies, node-internal prompts) remain static; single target distribution | Widen the edit space; evaluate over a sequence rather than a distribution |
| Static hand-built harnesses (Claude Code, Cursor, Manus) | Production-hardened; no evolution cost | Improve only through human iteration between releases | Not applicable |

## 4. Experimental Validation

### a) Experimental design

Five benchmarks (Table 3, Appendix A.1-A.2): GAIA Levels 1-3, 103 tasks (39/52/12), exact match; ALFWorld, all 134 tasks of the valid-unseen split, goal completion; WebShop, 100 instances at a fixed seed, attribute match; tau-cubed-Bench, three domains (Retail, Airline, Telecom), rule compliance; SWE-bench Verified, a 55-task subsample, patch resolution. Three task agents — Claude Sonnet 4.6, GPT-5.4, Qwen3.5-9B — against one meta-agent, Claude Opus 4.6, held fixed everywhere. Two baselines: a static harness built from published benchmark-specific prompts and tools, and a single-session Claude Code SDK evolver sharing the same model, round budget, and infrastructure (explicitly "a proxy for monolithic evolvers such as SICA").

Protocol (Table 8, Appendix A.4-A.5): up to 15 rounds with early stopping after 3 consecutive rounds without a shipped edit; 4 candidates proposed per round; 3 random seeds per cell; single-round pass-count deltas within 5% ignored as noise; the full task set re-evaluated every round with no subsampling; per-benchmark step limits (GAIA and WebShop 20, ALFWorld 15, tau-cubed-Bench and SWE-bench 200); task rollouts at concurrency 10, meta-agent at concurrency 4 with a 200-step limit per role; a fresh environment instance per task so side effects cannot leak; meta-agent token budget 100M-175M per benchmark, held constant across task agents within a benchmark. Round 0 is a competent composed harness with the benchmark's tool registry, not a minimal default, so reported gains are relative to a strong start. Co-evolution runs use 8 H100 GPUs, batch size 256, learning rate $1\times10^{-6}$, GRPO clip 0.2, **no Kullback-Leibler penalty (coefficient 0)**, 5 training steps per round, and a four-round sliding-window buffer (824 GAIA traces, 400 WebShop traces).

### b) Key results

1. **Headline (Table 4)**: evolution improves 14 of 15 model-benchmark configurations, average +14.5 percentage points, range 0.0 to +44.0. Largest cells: ALFWorld Qwen3.5-9B 53.0 to 97.0 (+44.0, best round 9), ALFWorld GPT-5.4 76.9 to 97.8 (+20.9, round 4), SWE-bench GPT-5.4 45.5 to 63.6 and Qwen3.5-9B 23.6 to 41.8 (both +18.2), WebShop GPT-5.4 55.0 to 73.0 (+18.0). Smallest: tau-cubed-Bench Qwen3.5-9B +1.1 (93.5 baseline, near ceiling) and GAIA GPT-5.4 exactly 0.0 over 15 rounds.
2. **Inverse scaling with baseline (Sec. 6.2, 7.4)**: on ALFWorld the same Opus 4.6 meta-agent yields +11.2 for Sonnet 4.6, +20.9 for GPT-5.4, +44.0 for Qwen3.5-9B — gain tracks inverse baseline performance, not proximity to the meta-agent's own model family.
3. **Single-harness evolution collapses on a heterogeneous task set (Table 5)**: on GAIA with GPT-5.4 over 15 rounds, the single-harness strategy peaks at 73.8% (round 4) and ends at 49.5% — a peak-to-final gap of -24.3 points, far outside the per-round binomial 95% interval of about ±8.5 at $n = 103$. Variant isolation over the same run ends at 87.4% with peak equal to final (gap 0.0) and consumes fewer tokens (107.8M vs 143.7M).
4. **Post-peak degradation is not confined to that one cell**: on SWE-bench Verified with GPT-5.4, evolution peaks at 63.6% (round 3) and degrades to 50.9% by round 5, -12.7 from peak, still +5.4 above the static baseline (Sec. 6.2). On tau-cubed-Bench Telecom with Sonnet 4.6, compliance rises 89.5% to 100% at round 4, falls to 94.7% by round 6, then to 80.7% at round 7 (-14.0), recovering to 99.1% by round 9 (Sec. 6.6, D.4).
5. **Co-evolution beats harness-only evolution (Sec. 6.5)**: peak success 37.4% to 41.7% on GAIA (+4.3) and 49.0% to 54.0% on WebShop (+5.0), average +4.7; the gap persists to the final round (GAIA 36.4 to 39.8, WebShop 46.0 to 50.0). The two curves coincide until joint training takes effect at round 4, then diverge.
6. **The four-stage pipeline buys efficiency, not accuracy (Table 6)**: AEGIS 87.4% at 107.8M tokens vs a single-agent evolver 86.4% at 123.1M tokens on GAIA, a 1.0-point gap the authors place within one standard error.

### c) Where it shines

Where a benchmark's failures concentrate in one or two component types, convergence is fast and durable: ALFWorld with GPT-5.4 peaks at round 4, SWE-bench at rounds 2-3. Where a single mechanical blocker dominates, one tool edit carries the round — Appendix C documents GAIA round 10, where replacing browser-based Wikipedia fetching with a MediaWiki API call (10,529 characters returned where the browser returned 0) lifted the round from 74.8% to 79.6%, five tasks flipping, the highest per-edit hit rate (0.71) of any shipped edit across 19 rounds. Appendix D quantifies which edit bucket pays per model: on ALFWorld the strong base model gains almost entirely from prompt edits (hit rate 0.49 for Sonnet 4.6) while the weak one needs structural edits (Qwen3.5-9B: processor 0.84, configuration 0.71, prompt 0.63); on GAIA the single Qwen3.5 tool edit is the highest-yield cell at 0.67.

### d) Limitations

**Acknowledged (Sec. 7.7 and elsewhere).** No held-out evaluation — "all reported gains are measured on the same task set used for evolution ... the numbers carry both selection bias and potential overfitting"; discrete text action spaces only; the meta-agent must be a closed-weight frontier model ("open-weight models approaching this capability level ... remain untested as meta-agents"); co-evolution needs joint control over harness evolution and model training, "often separated across teams or organizations"; small samples (55 SWE-bench tasks, 3 tau-cubed-Bench domains). Section 7.3 concedes the mirror does not predict which pathology will dominate or when. Section 7.5 reports the cost honestly: the GAIA single-harness run spent 143.7M meta-agent tokens across 15 rounds for a net gain of 0.0%.

**Most important for us, and stated by the paper itself.** Section 7.6: "The tau-cubed-Bench failure illustrates their limits: five consecutive same-type edits accumulated sub-threshold coupling undetected by the seesaw constraint; the sixth edit triggered a visible -14.0% regression, yet no individual edit violated the constraint. This is a structural limitation of per-edit gating: sub-threshold regressions accumulate undetected regardless of how many prior rounds have demonstrated apparent stability under the same constraint." Section 7.2 adds the diagnostic version: "Structured trace recording is therefore necessary for detecting pathologies, but not sufficient for preventing them: when coupling accumulates below the per-task detection threshold, traces record the symptoms only after damage has occurred."

**Unacknowledged.** Since every number is a peak on the adaptation set, the reported "average +14.5%" is a maximum over up to 15 correlated round estimates on one fixed task list — an upward-biased statistic even before the absence of held-out tasks is considered; the paper reports it without a selection correction. The comparison in Table 5 between variant isolation and the single-harness strategy varies two things at once (number of variants and the scoping of the retention check) and is run once on one benchmark with one task agent. The claim that the Planner is the defense against under-exploration is supported by one case study (ALFWorld rounds 4-7), not by an ablation removing the Planner. And the prompt-level guardrails in the released meta-agent — "no local-only optimization", "would this guidance help an agent solving a task it has never seen before?" — are load-bearing for generalization but are never tested against any unseen task.

## 5. Reproduction and Application

### a) Open source?

Yes: https://github.com/Darwin-Agent/HarnessX, MIT-licensed, v0.1.0 Beta, Python 3.11+, with a command-line entry point, a benchmark suite, and evolution recipes for GAIA, tau-cubed-Bench, and Terminal-Bench 2. Full component inventory in `repo_analysis.md`. Two gaps between paper and release matter for reproduction: the string "AEGIS" and the four stage names (Planner, Evolver, Critic) do not appear anywhere in the code at the cloned commit — the released evolver is a single meta-agent with a skills workspace, which is the shape of the paper's own single-agent comparison — and the released acceptance gate is an aggregate pass-rate comparison against the historical best, not the per-task seesaw constraint the paper describes. Cross-harness GRPO is likewise absent; the shipped reinforcement-learning recipes are standard multi-turn agentic GRPO on veRL and slime.

### b) Implementation details requiring attention

The evaluation set is re-scored in full every round, so the per-round cost is (tasks × rollouts × rounds) agent runs plus the meta-agent's budget; at pass@2 over 103 GAIA tasks and 15 rounds that is 3,090 agent runs plus 143.7M meta-agent tokens. Round 0 is a competent composed harness, so gains are not measured from a naive default. Pass@2 masks sub-threshold drift by construction — the authors name this as the mechanism behind their worst failure. The GRPO configuration uses no Kullback-Leibler penalty (coefficient 0) despite the objective in equation 4 carrying one, so the fixed reference model constrains nothing in the reported runs. Behavior log-probabilities must be cached at buffer insertion; they cannot be recovered later from any live checkpoint. In the released code the gate's tolerance defaults to 0.03 (3 percentage points of pass rate) with a cost weight of 0.0 and a rule that a rollback fires only when the tolerance is breached **and** at least 3 tasks flipped — three tunable numbers that together decide what counts as a regression.

### c) Transferability

Three pieces transfer to our setting with modification, and one confirms a design choice.

The **typed processor substrate with eight lifecycle hooks and singleton-group exclusion** is the most concrete existing answer to our open item on the exact proposer action space, and it is production code rather than a diagram. Our layer list (system prompt, tool description, tool implementation, middleware, skill, sub-agent configuration, long-term memory, model weights) is wider than their realized edit buckets (`prompt`, `tools`, `config`, `processor`) on three layers — sub-agent configuration, long-term memory content, and weights are outside the edit action space here, with weights moved only by the separate GRPO optimizer. Their four buckets are the intersection worth supporting first.

The **change manifest** transfers as an evaluation instrument, not as a plasticity mechanism. Requiring each proposed edit to name the tasks it will unlock, stabilize, and put at risk, plus a trace feature that must appear if the edit fired, gives per-edit precision and side-effect counts that are computable from logs. Their released journal already computes exactly this (`flipped`, `still_F`, `regressed`, `still_T`, `absent`, with unpredicted regressions added to the denominator). A decaying per-bucket hit rate is not a plasticity estimate — it is a property of the proposer, not of the harness state — but it is a cheap observable that their own under-exploration case study shows dropping from 80% to 0% over four rounds as the prompt edit space exhausts, which makes it a plausible input feature for a critic that reads harness state.

**Cross-harness grouping by task identity** solves a problem we will have if we ever train the task model alongside the harness agent: trajectories from harness versions with incompatible tool schemas can share one advantage group as long as each is replayed under the harness that produced it, so the policy gradient touches only model output tokens.

Finally, their negative result **confirms the direction of our objective**. The paper's own preferred fix for accumulated regression is variant isolation — fork a variant instead of rejecting the edit — which converts a stability problem into a routing problem and works on their fixed task list (peak equals final, 87.4%). Section 7.3 states its limit without hedging: "nothing guarantees this extends to longer horizons (where variants may over-specialize) or to task distributions whose inter-task dependencies prevent clean variant separation." A heterogeneous, non-stationary task stream is precisely such a distribution, and their own rejected alternative — the single harness whose edits are gated per-edit on the current batch — is the configuration that collapsed by 24.3 points.

## 6. Summary

### a) One-sentence core idea

Make the harness a typed substitutable object, then let a meta-agent edit it each round under a deterministic no-regression gate, reusing the traces to train the model too.

### b) Quick-reference pipeline

1. Build the agent as a model configuration plus a harness configuration; the harness is a list of small event-handling components attached to eight fixed points in the run loop, each component typed so it can be swapped without breaking the others.
2. Run the current harness on a batch of benchmark tasks; record every model call, tool call, and result, and score each task with a fixed verifier.
3. A meta-agent language model compresses the traces to per-task summaries, builds a picture of what is failing and which kinds of edit have not been tried, and writes up to four candidate edits — a prompt rewrite, a new tool, a new middleware component, or a retuned setting — each declaring which tasks it expects to fix and which it might break.
4. Run the candidates and accept one only if a fixed sequence of checks passes, ending with: it must not break any task that currently passes. Reject everything, and the harness is unchanged; stop after three such rounds.
5. Optionally keep several harness variants and route each task to the one that has done best on it, so an edit that helps one group and hurts another forks a variant instead of being discarded; optionally also train the model on the same recorded runs, grouping runs by task across harness versions.
