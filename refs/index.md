| HCL | *Harness Continual Learning: Continual Adaptation Beyond Model Parameters* ([paper.pdf](related-work/HCL/paper.pdf)) | method | ❌ no public code | Defines Harness Continual Learning (HCL): a frozen foundation model with a mutable harness (task interface, experience memory, inner skills, router) updated by an untrained proposer behind a commit gate requiring current-task improvement, bounded anchor damage, and validity. Evaluated on ALFWorld, Minecraft, textual and multimodal streams; the tolerance sweep shows forgetting rising monotonically while final performance peaks at an intermediate setting. Plasticity is named but never defined or measured; weights, tools, and the update machinery itself are never modified — our named falsifier baseline. | Agent-Harness-Survey | *Agent Harness Engineering: A Survey* ([paper.pdf](related-work/Agent-Harness-Survey/paper.pdf)) | empirical | ✅ [repo/](related-work/Agent-Harness-Survey/repo) · [src](https://github.com/Picrew/awesome-agent-harness) (catalog, not an implementation) | 71-page survey plus systematic mapping study: defines the harness as an engineering layer distinct from the model, proposes the seven-layer ETCLOVG taxonomy (execution, tooling, context, lifecycle, observability, verification, governance), and codes 171 catalogued open-source artifacts onto it; lifecycle, verification, and execution are dense, observability and governance thin, context tooling embedded. Names harness self-optimisation (Meta-Harness, observability-driven evolution, benchmark-gated loops) an open direction and warns that narrow-suite self-optimisation breeds brittleness; every instance it lists scores the current batch. The repo is the living catalog (367 entries, 9 categories, YAML plus render and verify scripts), a scan list for related self-improving harnesses and inspectable open harnesses. | Harness-Anatomy | *Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents — A Source-Code Study of Eleven Systems* ([paper.pdf](related-work/Harness-Anatomy/paper.pdf)) | empirical | ❌ no public code | Source-code audit of eleven production coding harnesses (Claude Code, Codex, Gemini CLI, Mistral Vibe, OpenHands, Aider, Mini-SWE-Agent, Hermes, Pi, OpenCode, OpenClaw) plus the Omnigent meta-harness, pinned to July 2026 with April snapshots diffed for eight of them; yields a seven-subsystem anatomy, 13 observations, 29 patterns, and 18 recommendations. Headline absences: no agentic framework and no embedding retrieval over code in any runtime; skills (9/11) lead MCP (8/11); convergence became imitation within one quarter. For us: the layer list is grounded in production, the three in-the-wild self-improving write paths (Codex agent-maintained memory, Hermes skill loop, Gemini CLI human-gated inbox) all score on current use and never on later tasks, and the pinned public git histories are human harness-evolution logs. [arXiv:2609.00006](https://arxiv.org/abs/2609.00006) | [paper_analysis.md](related-work/Harness-Anatomy/paper_analysis.md) |
| Adaptive-Auto-Harness | *Adaptive Auto-Harness: Sustained Self-Improvement for Agentic System Deployment on Open-Ended Task Streams* ([paper.pdf](related-work/Adaptive-Auto-Harness/paper.pdf)) | method | ✅ [repo/](related-work/Adaptive-Auto-Harness/repo) · [src](https://github.com/A-EVO-Lab/a-evolve/tree/release/adaptive-auto-harness) | Splits the gap to an oracle harness into evolution loss (what the evolver class cannot build) and adaptation loss (committing to one harness before seeing the task), then attacks them with a four-role stateful evolver (analyze, research, build, verify) and a git-branch harness tree with solve-time agentic routing, plus human hooks for signals history cannot contain. Evaluated on three real chronological streams (PolyBench 5,075 prediction markets, CTF-Dojo 261 security challenges, FutureX 503 forecasting questions), beating five auto-harness baselines (80.9% PolyBench accuracy vs 22.2% no-evolution and 18.4% A-Evolve). The code is a complete, runnable system: the three stream adapters with delayed-label reveal, a two-method pluggable solve-time adaptation seam with four operators, per-cycle git tags that form a harness-evolution log, and near-empty seed harnesses (27/24/114 prompt lines, zero skills/tools/memory). For us: the closest prior system to our setting and still the greedy case: every edit is scored on the batch that made it, all 39 configs disable the inherited holdout gate, branch merge and pruning are declared in config and implemented nowhere, and its own runs peak at cycle 22 of 51 and then decline. [arXiv:2606.01770](https://arxiv.org/abs/2606.01770) | [paper_analysis.md](related-work/Adaptive-Auto-Harness/paper_analysis.md) · [repo_analysis.md](related-work/Adaptive-Auto-Harness/repo_analysis.md) |
| Harness-R1 | *Harness-R1: Learning to Edit Executable Runtime Harnesses from Agent Failure Trajectories* ([paper.pdf](related-work/Harness-R1/paper.pdf)) | method | ✅ [repo/](related-work/Harness-R1/repo) · [src](https://github.com/DeepExperience/Harness-R1) | Post-trains a dedicated 9B harness engineer (cold-start SFT on 877 filtered teacher patches, then online GRPO with 8 candidates per failure packet) to read a frozen target agent's failure traces and emit sandboxed Python hooks at four episode-lifecycle points (episode start, pre-decision, pre-action, post-feedback); the reward installs the patch and reruns the same batch with the same frozen target, making it the purest horizon gamma = 0 objective in this index and additionally the inverse of score-before-update. Benchmark average 44.3 to 53.6 on WebShop/ALFWorld/DBBench, +7.06 points across twenty unseen targets, and +8.9 ± 1.5 points on 1,270 held-out tasks where prompted frontier editors average −4.3 and −0.4. The repo ships the whole pipeline: a 388-line AST sandbox for model-written hooks, three same-batch rerun reward functions, the GRPO launcher, two engineer checkpoints, and 23 (harness edit, realized held-out outcome) pairs spanning three editor qualities. Nothing accumulates across batches (the paper's own phrase is "no persistent patch memory across batches"), so there is no harness state that could lose plasticity, and Sec. 5 names held-out reward as its own future work.
