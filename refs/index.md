| HCL | *Harness Continual Learning: Continual Adaptation Beyond Model Parameters* ([paper.pdf](related-work/HCL/paper.pdf)) | method | ❌ no public code | Defines Harness Continual Learning (HCL): a frozen foundation model with a mutable harness (task interface, experience memory, inner skills, router) updated by an untrained proposer behind a commit gate requiring current-task improvement, bounded anchor damage, and validity. Evaluated on ALFWorld, Minecraft, textual and multimodal streams; the tolerance sweep shows forgetting rising monotonically while final performance peaks at an intermediate setting. Plasticity is named but never defined or measured; weights, tools, and the update machinery itself are never modified — our named falsifier baseline. | Harness-Anatomy | *Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents — A Source-Code Study of Eleven Systems* ([paper.pdf](related-work/Harness-Anatomy/paper.pdf)) | empirical | ❌ no public code | Source-code audit of eleven production coding harnesses (Claude Code, Codex, Gemini CLI, Mistral Vibe, OpenHands, Aider, Mini-SWE-Agent, Hermes, Pi, OpenCode, OpenClaw) plus the Omnigent meta-harness, pinned to July 2026 with April snapshots diffed for eight of them; yields a seven-subsystem anatomy, 13 observations, 29 patterns, and 18 recommendations. Headline absences: no agentic framework and no embedding retrieval over code in any runtime; skills (9/11) lead MCP (8/11); convergence became imitation within one quarter. For us: the layer list is grounded in production, the three in-the-wild self-improving write paths (Codex agent-maintained memory, Hermes skill loop, Gemini CLI human-gated inbox) all score on current use and never on later tasks, and the pinned public git histories are human harness-evolution logs. | Adaptive-Auto-Harness | *Adaptive Auto-Harness: Sustained Self-Improvement for Agentic System Deployment on Open-Ended Task Streams* ([paper.pdf](related-work/Adaptive-Auto-Harness/paper.pdf)) | method | ✅ [repo/](related-work/Adaptive-Auto-Harness/repo) · [src](https://github.com/A-EVO-Lab/a-evolve/tree/release/adaptive-auto-harness) | Splits the gap to an oracle harness into evolution loss (what the evolver class cannot build) and adaptation loss (committing to one harness before seeing the task), then attacks them with a four-role stateful evolver (analyze, research, build, verify) and a git-branch harness tree with solve-time agentic routing, plus human hooks for signals history cannot contain. Evaluated on three real chronological streams (PolyBench 5,075 prediction markets, CTF-Dojo 261 security challenges, FutureX 503 forecasting questions), beating five auto-harness baselines (80.9% PolyBench accuracy vs 22.2% no-evolution and 18.4% A-Evolve). The code is a complete, runnable system: the three stream adapters with delayed-label reveal, a two-method pluggable solve-time adaptation seam with four operators, per-cycle git tags that form a harness-evolution log, and near-empty seed harnesses (27/24/114 prompt lines, zero skills/tools/memory). For us: the closest prior system to our setting and still the greedy case: every edit is scored on the batch that made it, all 39 configs disable the inherited holdout gate, branch merge and pruning are declared in config and implemented nowhere, and its own runs peak at cycle 22 of 51 and then decline. | Harness-R1 | *Harness-R1: Learning to Edit Executable Runtime Harnesses from Agent Failure Trajectories* ([paper.pdf](related-work/Harness-R1/paper.pdf)) | method | ✅ [repo/](related-work/Harness-R1/repo) · [src](https://github.com/DeepExperience/Harness-R1) | Post-trains a dedicated 9B harness engineer (cold-start SFT on 877 filtered teacher patches, then online GRPO with 8 candidates per failure packet) to read a frozen target agent's failure traces and emit sandboxed Python hooks at four episode-lifecycle points (episode start, pre-decision, pre-action, post-feedback); the reward installs the patch and reruns the same batch with the same frozen target, making it the purest horizon gamma = 0 objective in this index and additionally the inverse of score-before-update. Benchmark average 44.3 to 53.6 on WebShop/ALFWorld/DBBench, +7.06 points across twenty unseen targets, and +8.9 ± 1.5 points on 1,270 held-out tasks where prompted frontier editors average −4.3 and −0.4. The repo ships the whole pipeline: a 388-line AST sandbox for model-written hooks, three same-batch rerun reward functions, the GRPO launcher, two engineer checkpoints, and 23 (harness edit, realized held-out outcome) pairs spanning three editor qualities. Nothing accumulates across batches (the paper's own phrase is "no persistent patch memory across batches"), so there is no harness state that could lose plasticity, and Sec. 5 names held-out reward as its own future work. | SIA | *SIA: Self Improving AI with Harness & Weight Updates* ([paper.pdf](related-work/SIA/paper.pdf)) | method | ✅ [repo/](related-work/SIA/repo) · [src](https://github.com/hexo-ai/sia) | A three-agent loop (Meta-Agent, Task-Specific Agent, Feedback-Agent) that improves one fixed task by alternating two levers: rewriting the whole scaffold, or adapting the base model's weights by reinforcement learning with the scaffold fixed; the only system claiming to edit both (Table 1). Harness-only improvement plateaus on all three tasks and the plateau triggers the weight switch; harness-only fails to reach prior best on two of three (Table 3: LawBench 50.0% vs 70.1%, TriMul 0.120 vs 1.475, denoising 0.241 vs 0.289). The code is a readable ~9.5k-line orchestrator with a clean task/grader contract and golden-file prompt pinning, but the paper's per-step lever selector is absent (`--focus` takes harness or weights and is a launch flag fixed for the whole run) and there is no gate, no revert, and no retention check anywhere. Our purest horizon-zero case: every edit scored on the same fixed batch, best generation picked after the fact. [arXiv:2605.27276](https://arxiv.org/abs/2605.27276) · [OpenReview gZYsloW2bu](https://openreview.net/forum?id=gZYsloW2bu) (ICML 2026 Workshop AI4Research poster, shorter "SIA-W" version) | [paper_analysis.md](related-work/SIA/paper_analysis.md) · [repo_analysis.md](related-work/SIA/repo_analysis.md) |
| AHE | *Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses* ([paper.pdf](related-work/AHE/paper.pdf)) | method | ✅ [repo/](related-work/AHE/repo) · [src](https://github.com/china-qijizhifeng/agentic-harness-engineering) (Agent Debugger only partially released) | Closes the harness-improvement loop over all seven non-weight layers at once (system prompt, tool description, tool implementation, middleware, skill, sub-agent, long-term memory) laid out as files in a git workspace, with rollouts distilled into per-task root-cause reports and every edit shipping a manifest that names the tasks it should fix and the tasks it may break, checked by intersection against the next round's deltas. From a nine-line seed it reaches 77.0 pass@1 on Terminal-Bench 2 (seed 69.7, Codex 71.9) in ten rounds, and the frozen harness transfers to SWE-bench-verified at 12% fewer tokens. The repo ships the whole loop in one 4719-line `evolve.py`, the seed and evolved harnesses side by side for diffing, and a portable HARNESS.md v1.0 spec with a change-manifest schema. For us it is the strongest gamma = 0 exemplar and its own counter-evidence: the loop computes a retention rate and only prints it, "rollback" is the proposer's own judgement rather than a gate, the reported 77.0 is an argmax over a run that peaks at round 8 and declines, and the agent predicts regressions at 11.8% precision against a 5.6% chance baseline. | AgentStream | *AgentStream: How Well Do Self-Evolving LLM Agents Perform Under Streaming Tasks?* ([paper.pdf](related-work/AgentStream/paper.pdf)) | empirical | ✅ [repo/](related-work/AgentStream/repo) · [src](https://github.com/Jasper-Yan/AgentStream) | Streaming evaluation of five self-evolving methods (ACE, A-Mem, ReasoningBank, AutoSkill, and a harness arm the authors implement) crossed with three frontier models and three stream shapes (Isolated, Sequential, Interleaved) over 300 tasks from six agentic benchmarks, each task scored with the state as it stood before it arrived and compared against a stateless control. Average gains are only +0.75 to +1.37 points and 44 of 135 configurations fall below doing nothing; the sign is gated by model capability, the mixed stream beats the ordered one, and the harness arm is the only method with a negative gain under ordered domain shift (−0.86, Table 5). The repo ships the stream constructor, all five method implementations, six benchmark adapters with pinned splits, a no-state baseline runner, and per-task metrics including running cumulative accuracy and harness size in characters, but no result files at all, so every number must be regenerated against paid APIs. For us it is the ready-made score-before-update stream protocol and the undiscounted stream-performance integral, with code-level confirmation that no method passes any score into its update (the gamma = 0 case); it never re-tests a task, so it measures no retention, and it proposes an evaluation instrument rather than nothing.
